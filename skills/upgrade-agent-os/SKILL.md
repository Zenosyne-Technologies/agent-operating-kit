# Upgrade a Marvin (Agent Operating Kit) install

Current templates: `${CLAUDE_PLUGIN_ROOT}/templates/`. Never overwrite project-specific content — same merge discipline as install.

## Steps

1. **Detect installed state**: read `kit_version` from `.marvin/PROJECT-INFO.md` frontmatter. No stamp? Read `.docs/PROJECT-INFO.md` (pre-v0.21.0 location) before concluding none exists. Fingerprint once: cascade at `docs/agents/` vs `.docs/agents/` vs `.marvin/agents/`; `found-by:` present in taxonomy files (pre-registry); missing `label-syntax.md` / `tracker-config.md` / `planning-research.md` / `PROJECT-INFO.md`; list-style PROJECT-INFO without frontmatter. Report what was detected before changing anything.
2. **Diff by upgrade files**: read `${CLAUDE_PLUGIN_ROOT}/upgrades/` and apply, in semver order, every file AFTER the installed version up to and including the current one — each lists the consumer-visible steps; files stating "No consumer-visible changes" are skipped. Fall back to diffing against `${CLAUDE_PLUGIN_ROOT}/templates/` only where a step is ambiguous or the install predates version stamps (step 1 heuristics). Also track the label-registry delta (installed `label_syntax_version` → current registry H1).
3. **v0.20.0 → v0.21.0 layout migration** — run `bash ${CLAUDE_PLUGIN_ROOT}/scripts/migrate-v0.21.0.sh` from the consumer repo root and read its report. Never perform the moves, the rewrite or the commit by hand: this step is **unattended authority over someone else's repository**, every guard in the script was earned by a reproduced failure, and a hand-transcribed variant is exactly how those failures happened. Preview with `--check` first if the user wants to see the plan — a dry run changes nothing and works on a dirty tree too (the flags are mutually exclusive; `--check --no-commit` exits 4 without touching anything). Exit **0** done (or already migrated, a clean no-op) · **2** the tree is dirty: a real run refuses to start (with `--check` the plan was still printed) — show the paths, tell the user to commit or stash **themselves**, and skip to step 4 · **3** completed with destination collisions · **4** bad flags / not a git work tree · **5** a move failed. Carry every `declined:` and `collision:` line into the step-7 report verbatim, each named in full; collisions are reconciled by the user on their own data, never by you. Do not re-run the script to "fix" a collision — it will report it again. § *Migration mechanics* below is the rationale, not a procedure to replay.
4. **Migrate remaining repo files** (no confirmation — git-revertible): add missing cascade files INCLUDING the selected tracker's `tracker-config.md` and `stats-collection-brief.md` (from `${CLAUDE_PLUGIN_ROOT}/templates/pm/<tracker>/`, installed to `.marvin/agents/`), and the three `.docs/handbooks/<audience>/index.md` skeletons where missing, with placeholders resolved, and `.marvin/MEMORY.md` where missing; remove kit-installed persona copies from `.claude/agents/` where present (the seven v0.18.0 files — developer, developer-small, validator-completion, validator-security, researcher, documenter, ponytail — now ship WITH the plugin as `marvin:*` agents; only delete files whose content matches the kit's, never a project's own agent); merge CLAUDE.md rule updates without touching project rules; convert a legacy PROJECT-INFO to frontmatter form per the `project-info` skill. Autocommit (attribution per project settings).
5. **Sync tracker structure**: re-dispatch the installed tool's intake brief (idempotent — linear, jira, github, local; sources under `${CLAUDE_PLUGIN_ROOT}/templates/pm/<tracker>/`) as a sub-agent to seed new labels and refresh the guide. Skip when `pm_tool: none` (legacy); `local` dispatches its brief like any other tool. A `none` install may adopt the Local tracker — offer it, and on yes set `pm_tool: local` + install the local tracker files and dispatch its brief (project-key flow per `${CLAUDE_PLUGIN_ROOT}/templates/pm/INSTALL.md`).
6. **Gated data migration**: if the registry delta includes supersessions (mappings in the registry changelog, e.g. `found-by:agent-qa → origin:agent-qa`, `found-by:owner → origin:architect-request`), query the tracker for the affected-issue count and ask ONE yes/no. Yes → dispatch a ponytail (micro-tier) relabel sweep with the mapping as prepared payload. No → report the pending sweep and mapping. Never sweep unasked.
7. **Restamp + report**: update `kit_version` (from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`) and `label_syntax_version` in the frontmatter; commit. Report: from→to versions, files migrated, **every file the migration DECLINED to move (consumer-owned) and every destination collision, each named in full**, labels seeded (from the brief's machine message), sweep executed/pending/none, telemetry opt-in offered (when the token-telemetry plugin is present but `.claude/telemetry` is absent; when the plugin itself is absent — `claude plugin list` — advise installing it: `claude plugin install token-telemetry@emprove`, restart for hooks, with one line on the cost-aware features it adds; the restart rule ALSO applies when the upgrade enables telemetry — capture starts next session, say so), and — if Jira and the connector now supports release creation — that the `convert-milestones` brief is ready to dispatch.

## Migration mechanics (step 3)

Why the migration is a script and not a checklist: every defect ever found in this step was a transcription failure — a rule dropped, a rule applied one scope too wide, a rule inconsistent with its sibling. `scripts/migrate-v0.21.0.sh` holds the guards; `scripts/test-migrations.sh` pins each one to the failure it prevents. Read them if you need the detail. What you need to understand to interpret the report:

- **A dirty tree is refused, and never stashed.** "git-revertible" — the justification for running unattended in someone else's repository — is FALSE on a dirty tree: the consumer's WIP would land in the migration commit and their later `git revert` would destroy it. A stash you create is a stash they don't know to pop, so the refusal is theirs to clear.
- **The two destination guards differ on purpose.** A *real* move treats a destination as occupied if it is in the index **or** on disk: a consumer who hand-migrated with `cp` (or whose `.marvin/` is gitignored) leaves an untracked destination that an index-only guard walks straight past, and the move then nests into `.marvin/agents/agents/`. The *case-only* handbook rename uses the index **only**: `INDEX.md` and `index.md` are the same inode on a case-insensitive filesystem, so a disk test is already true before the rename and would silently skip it — shipping `INDEX.md` and breaking case-sensitive checkouts. Verify results with `git ls-files`, never `ls`: `ls` prints the old casing.
- **Kit files move, consumer files do not — and neither do their references.** `.docs/agents/` may hold a runbook or project notes. Moves run file-by-file against the kit's cascade allowlist; everything else is reported as declined and stays exactly where it is, with every reference to it left pointing at where it actually lives. Same for anything that collided: a reference is only retargeted when the file behind it actually moved.
- **Collisions are reported, never resolved.** No recursive delete happens during a migration, on either side of a collision or to "clean up". Reconciling is the user's call on their own data.
- **The rewrite is scoped.** `INDEX.md` → `index.md` applies only inside `.docs/handbooks/…` paths — a blanket pass corrupts a Local-tracker `tracker-config.md`, whose `.docs/project-management/INDEX.md` stays uppercase; lowercase it and the filing agent finds no index, creates one at `next_issue: 1`, and overwrites existing issue files.
- **One commit, staged by explicit path.** Renames and the CLAUDE.md rewrite are atomic, so the `git revert` escape hatch restores a *consistent* state rather than files in one place and references pointing at another.

The step is **idempotent and resumable**: an interrupted case-only rename leaves a `__index.tmp` the next run completes from, and a second run performs 0 moves, leaves `git status --short` empty and HEAD unchanged.

## Rules

- Steps 1–5 and 7 run without confirmation; step 6 is the ONLY interactive gate (shared tracker state is not git-revertible).
- Re-running on a current install must be a clean no-op (report `already at <version>`).
- Installed files stay self-contained: never write `${CLAUDE_PLUGIN_ROOT}` paths into the consumer repo.
