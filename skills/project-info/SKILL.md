# Project info page — create or validate

Template source of truth: `${CLAUDE_PLUGIN_ROOT}/templates/marvin/PROJECT-INFO.md`. Target: `.marvin/PROJECT-INFO.md`.

**Locate before you conclude — the pre-v0.21.0 fallback.** Absent from `.marvin/`? Read `.docs/PROJECT-INFO.md`, then `docs/PROJECT-INFO.md` (pre-v0.21.0 locations) before concluding none exists. Whichever of the three you find FIRST is *the* file — there is exactly one PROJECT-INFO in a repo, because its frontmatter is the machine contract foreign agents and reporting tools parse. Creating a second one at `.marvin/` while the real one sits at `.docs/` is the failure this fallback exists to prevent: the v0.21.0 migration then refuses the move as a destination collision (exit 3), and `upgrade-agent-os` step 1 reads the NEW stamp, finds no upgrade file past it, and does nothing — leaving the cascade stale in `.docs/agents/`, `.marvin/agents/` empty, and every `marvin:*` persona pointing at a path that does not exist.

**Found at a legacy location → validate it THERE, in place, and do not move it.** Relocating is `upgrade-agent-os`'s job, not this skill's: the migration script stages the rename atomically with the reference edits that must land in the same commit. Validate and fix as below, then report — in words — that this install is on the pre-v0.21.0 layout and needs the `upgrade-agent-os` skill, naming the path you validated. The same fallback applies to every fact source this skill reads: `.marvin/agents/*`, else `.docs/agents/*`, else `docs/agents/*`.

## If NO file exists at any of the three locations → create

1. Gather every fact from the repo itself: name/description (manifest, README), `brief` (a short "what is this" from the README/description — free text), owner, layout, tech stack, dev command + ports; PM tool, coordinates, hierarchy, and guide URL from the installed `tracker-config.md` + `ticket-filing.md` if present; label-syntax version from the installed `label-syntax.md`. Ask only for facts that are truly undiscoverable.
2. **Only after `.marvin` and the file pass the `upgrade-agent-os` skill's Rules *Symlink precondition* and *Commit scope*'s clean-path test** (`${CLAUDE_PLUGIN_ROOT}/skills/upgrade-agent-os/SKILL.md`; cited, not restated), write `.marvin/PROJECT-INFO.md` from the template with every placeholder resolved — every YAML frontmatter key filled (`kit_version` from the plugin's `.claude-plugin/plugin.json` when installed via plugin, else the kit repo's; `label_syntax_version` from the installed `label-syntax.md`'s H1; `screens_guide` → the UI screen catalog pointer, default `.docs/handbooks/developer/screens/index.md`; `visual_validation` → `per-task` | `milestone` | `off`, default `per-task`; `issue_log_path` → the install skill's step-2 rule, `.docs/issue-log.md` by default — never read from `CLAUDE.md` prose); body stays facts-only prose, no operating rules.
3. Commit it (autocommit policy, attribution per the project's settings) per *Commit scope*: `git add -- .marvin/PROJECT-INFO.md`, then `git commit -- .marvin/PROJECT-INFO.md` — never a plain `git commit`, which would sweep in whatever the consumer had staged. Report the created path and any unresolved placeholder.

## If the file EXISTS (at any of the three) → validate, then fix via sub-agent — never recreate

Do NOT overwrite, regenerate, restructure or relocate the existing file.

1. **Validate**: the YAML frontmatter parses and contains every template key (extra project-specific keys are fine — leave them); each frontmatter fact checked against the repo — `stack`, `dev_command`, `tracker_coordinates`/`project_key`/`hierarchy_levels` (vs the installed `tracker-config.md`), `intake_guide_url`, `label_syntax_version` (vs the registry H1), `docs_location`, `telemetry` (`enabled` iff `.claude/telemetry` exists, else `disabled`); body statements must not contradict frontmatter. `brief`, `description`, `audience`, `project_size` and `app_type` are descriptive free-text/enum facts — check they are PRESENT and non-empty (add the key with a sensible value or `n/a` if missing), but do not "correct" prose that merely reads differently from the repo. `screens_guide` (UI screen-catalog pointer, default `.docs/handbooks/developer/screens/index.md`) and `visual_validation` (`per-task` | `milestone` | `off`, default `per-task`) are checked PRESENT — add with the default when missing. `issue_log_path` is read from the frontmatter ONLY — this skill never reads `CLAUDE.md` prose: missing on a legacy install not yet upgraded → leave it unset and tell the user to run `/marvin:upgrade-agent-os`, whose step 4a adds it; present → check it is a bare repo-relative path inside `.docs/` per the install skill's step 2. **`kit_version` is NOT auto-corrected here**: a stamp that disagrees with the layout on disk is a finding for `upgrade-agent-os`'s tie-break (the layout wins), and restamping it from this skill would hide the pending upgrade.

   **Legacy page (no frontmatter)**: treat every missing key as a discrepancy — the fix sub-agent adds the frontmatter block from the template (facts lifted from the existing list) and keeps project-specific extras in the body; the file is converted, never regenerated.
2. **Fix automatically**: if there are discrepancies, dispatch ONE sub-agent (micro tier — mechanical zero-discretion work; brief per the installed ponytail profile where available) with the prepared corrections as its payload: exact line-level edits only (`field → new value`), add missing template fields, never touch correct lines or project-specific extras. Before dispatching, the file you found and its ancestors pass the *Symlink precondition* and the clean-path test (step 2 above cites both). The sub-agent commits its fix (autocommit policy, attribution per the project's settings) per *Commit scope* — `git add --` then `git commit --` that one path — and, when an install or upgrade run in progress already changed the file (a PROJECT-INFO its migration moved), commits nothing and leaves the fix to that run's commit; the dispatch says so.
3. **Report**: the path validated (and that it is the legacy location, where it is), `valid` or the count of corrections applied and the fix commit that holds them (the `field → old → new` detail stays in that commit, never copied into chat), any fact that stayed unfixable (truly undiscoverable) for the user to fill in, and any stamp-vs-layout disagreement you saw.
