Getting started

Install Marvin and run your first session

Add the marketplace, install the plugin, then ask for the install in any project. This page covers the install, the first session, choosing a PM tool, installing by hand, upgrading, what the plugin's hooks do, and Windows.

Install

Marvin is served by the standalone emprove marketplace (Zenosyne-Technologies/emprove-marketplace on GitHub):

# 1. add the marketplace (one time)
claude plugin marketplace add Zenosyne-Technologies/emprove-marketplace

# 2. install Marvin, plus the optional cost-telemetry companion
claude plugin install marvin@emprove
claude plugin install token-telemetry@emprove

# 3. in a project folder, run the install skill
/marvin:install-agent-os

Ask /marvin:info at any time for a read-only report of the plugin version, the current project's install state and its active settings.

Your first session

In any project, just ask: "install the agent operating kit into this project", or run /marvin:install-agent-os directly. The install:

  • reads the repo's own facts to resolve every placeholder;
  • merges with what already exists instead of overwriting it;
  • asks which PM tool the project uses (below) and which model profile it runs (model_profile);
  • proves that tool is reachable from the session before installing anything for it;
  • dispatches a sub-agent to build the tracker's intake structure.

A greenfield repo gets a short interview. When the target carries no source yet (only config, docs and maybe empty build manifests), the install has no code to read its facts from, so it asks four quick questions instead: who the users are, the rough project size, the application type, and the tech stack. Answer "no stack in mind" and it offers a handful of coherent, popular stack combinations, each with its reason. The answers land in .marvin/PROJECT-INFO.md as audience, project_size, app_type and stack. A brownfield repo (one that already has source) finds all of that in the code and skips the interview.

A greenfield install can also scaffold. As its last step it asks whether to scaffold the chosen stack now, or lay down the project and Marvin files only. Choosing to scaffold opens a tracked "Milestone 0: scaffolding and installing project dependencies". The plan is written down first. Then the scaffold and its dependency install run as ordinary Marvin tasks through the full lifecycle (plan, build, validate, document, close), dependencies included, because env wiring is part of the feature. A files-only answer, or any brownfield install, skips scaffolding and goes straight to the commit.

From then on, Marvin plans, briefs and verifies every task. The task lifecycle shows what happens to a task, and Settings lists every key the install wrote.

Choosing a PM tool

The kit targets a four-level hierarchy: milestone, then epic or feature grouping, then work item, then sub-item.

ToolHierarchyNative mirroringNotes
Linear4/4 native: Project → Milestone → Issue → Sub-issueseverity → Linear PriorityLabels and the in-tracker intake guide are created by the intake brief.
Jira3/4 plus virtual milestones: a milestone:<slug> label on every epicseverity → Jira Priority, or JSM ImpactThe milestone encoding converts losslessly: convert-milestones-brief.md is ready to dispatch the moment the connector can create releases.
GitHub Issues4/4 native: Milestone → parent issue → issue → task listno priority or estimate field to mirrorLabels seeded through the gh CLI; the intake guide lives as a pinned issue.
Local4/4 via files: milestone file → epic issue with children: → issue file → task-list checkboxno native fields to mirror; labels live in frontmatterA fully self-contained markdown tracker inside the repo. No external service, no auth.

Which tool a project uses is always your choice, never inferred, even when exactly one tracker happens to be connected. The install checks the choice straight away, before it installs anything for it: the MCP tools resolve and one cheap authenticated read works for Linear and Jira, gh auth status and a repo lookup work for GitHub, and Local needs nothing. If the check fails you are told plainly and offered three ways forward: pick another tool, connect it and install later, or fall back to Local now and adopt the external tool later with an upgrade and an intake re-run. The fallback is never silent.

Installing without the plugin

No plugin, four steps, and the first one runs FIRST:

  1. Already have an older install? Migrate before you copy anything. If the cascade sits in docs/agents/ or .docs/agents/, do NOT move anything by hand. Run bash scripts/migrate-v0.21.0.sh from the repo you are upgrading (--check first for the plan). It moves and stages the kit's files and prints a rename map. You then update the references it lists, judging each hit in context, and commit your edits together with the staged renames.

    The order matters. The script refuses a dirty tree (exit 2) and reports a collision for every destination a copy already occupies, so copying first makes it impossible to run: 13 collisions and 0 renames on a v0.20.0 layout.

    If .docs/reports/ holds anything, run bash scripts/migrate-v0.35.0.sh the same way. It moves EVERY file there to the same path under .marvin/reports/, consumer-written reports included, but only after the first migration is committed: each refuses the other's staged moves as a dirty tree, and it refuses untracked or gitignored files under .docs/reports/ too (exit 2, named on untracked: lines). On exit 2 or 9, stop, clear what it names, and start again here. Nothing below is a fresh-install-only step; a clean repo simply has nothing to migrate.

  2. Copy the payload.

    • templates/marvin/agents/ → <repo>/.marvin/agents/; your PM tool's templates/pm/<tracker>/tracker-config.md and stats-collection-brief.md → <repo>/.marvin/agents/; Jira only, templates/pm/jira/convert-milestones-brief.md → <repo>/.marvin/agents/.
    • templates/marvin/PROJECT-INFO.md and templates/marvin/MEMORY.md → <repo>/.marvin/.
    • The estate seeds file by file, NOT as a directory copy: templates/docs/index.md (the crawl's entry point), templates/docs/{plans,researches,refactor,future,information,release-notes}/index.md and templates/docs/handbooks/index.md each → the same path under <repo>/.docs/. Then templates/docs/handbooks/audience-index.md → <repo>/.docs/handbooks/developer/index.md, …/user/index.md and …/admin/index.md (three copies under that one name). audience-index.md itself is never placed in .docs/: an unindexed file there is unreachable by the crawl, which means it does not exist.
    • An index the repo already has is merged: keep its rows and prose, and add only the rows it lacks (the missing sub-folder rows, and the ## Root-level documents section with its issue-log row where that section does not exist yet).
    • templates/marvin/CLAUDE.marvin.md → <repo>/.marvin/CLAUDE.marvin.md (the kit core, refreshed on every upgrade; never edit it).
    • templates/CLAUDE.project.md → <repo>/CLAUDE.md. An existing CLAUDE.md keeps every line and gains only the stub's missing project-rules items plus the bare import line @.marvin/CLAUDE.marvin.md as its LAST line, never in backticks or a code block (Claude Code skips imports there). A repo with only an AGENTS.md gets the stub with @AGENTS.md directly above that import.
    • templates/settings.json → <repo>/.claude/settings.json, merging if one exists.
    • Finally, list every .md under .docs/ (outside project-management/) that no index row reaches. Give each an index row where its folder is obvious, and name the rest: under these rules an unindexed document cannot be found.
    • Add .marvin/runs/ to <repo>/.gitignore. Sub-agent run reports live there and are never committed; .marvin/reports/ beside it holds the committed reports and is never ignored.

  3. Fill every {{PLACEHOLDER}} in the copied files: project facts, env preamble, tracker coordinates, {{INSTALL_DATE}} (today, in every header), and {{DOCS_ISSUE_LOG_PATH}}. That last one has ONE form, a bare repo-relative path, .docs/issue-log.md by default. The root index's record row already carries its default link target and holds no placeholder, so retarget that cell only for a non-default log, and delete the row unless the path resolves inside .docs/ and outside project-management/. {{SCOPE}} and {{PERIOD_DAYS}} in stats-collection-brief.md stay unresolved on purpose: they are filled at dispatch. Delete rules that do not apply; add project-specific "conventions that bite" as you learn them.

  4. Create the tracker structure. Hand an agent your PM tool's templates/pm/<tracker>/intake-structure-brief.md with the placeholders filled. It works as a small-model task.

Or paste BOOTSTRAP.md into a Claude session: it is a pointer that walks the session through the install skill directly.

Updating and upgrading

Installed plugins are pinned snapshots: pushing commits to the kit repo does not update installed copies. Two things have to happen:

  1. The plugin version gets bumped in the plugin manifest with every release, which the kit's own rules require. Claude Code resolves updates by that version string; new commits under an unchanged version are invisible to installed copies.
  2. You pull the update (the CLI and the desktop app behave the same):
claude plugin marketplace update emprove     # refresh the marketplace clone
claude plugin update marvin@emprove

Or enable auto-update once: /plugin → Marketplaces → emprove → Enable auto-update, which is off by default for third-party marketplaces. New sessions then load the updated plugin; an already-open CLI session needs /reload-plugins.

Updating the plugin does not touch projects you already installed into. Run /marvin:upgrade-agent-os in each repo to bring its installed files to the current version. That skill walks the per-release notes under upgrades/ in order, so a project several versions behind still gets every migration step applied. /marvin:whats-new explains what changed between this project's version and the plugin's (or any two versions), Action needed first, and Releases has every version's notes.

From v0.21.0, upgrade promptly in every repo. The marvin:* personas read .marvin/agents/* with a fallback to the pre-v0.21.0 .docs/agents/ location, so a repo not yet upgraded falls back to its older installed guides rather than breaking. That fallback is a safety net, not a substitute for upgrading: only the upgrade run refreshes those guides to the current version and adds new ones. The plugin update alone fixes nothing inside a project.

From v0.33.0, the kit's rules live in .marvin/CLAUDE.marvin.md, not in CLAUDE.md. CLAUDE.md is yours: project facts, your project rules, and one bare line, @.marvin/CLAUDE.marvin.md. That is Claude Code's native import, resolved relative to CLAUDE.md and loaded at session start with no prompt. The kit file is kit-owned, so every upgrade refreshes it like any .marvin/agents/ guide, and no release asks you to re-sync CLAUDE.md by hand again.

The first upgrade to v0.33.0 splits your existing CLAUDE.md once. A read-only planner (scripts/plan-claude-md-split.sh) classifies every line, and the upgrade asks ONE confirmation question before it writes anything at all. It keeps a verbatim backup under .marvin/backups/, removes only the kit's own lines, lets you keep or drop each customised kit rule it flags for review, and appends the import; declining writes nothing but the report. Project rules in CLAUDE.md refine the kit's; the kit's safety gates cannot be switched off from there. Imports nest at most four hops: CLAUDE.md → the kit core is one, and the kit core imports nothing. Keep .marvin/ tracked: a gitignored kit file makes the import load nothing in every other clone.

AGENTS.md is supported only through CLAUDE.md. Claude Code reads AGENTS.md only when no CLAUDE.md exists, so a CLAUDE.md that should honour it carries an @AGENTS.md line (the install adds it when it creates CLAUDE.md beside an existing AGENTS.md). The kit never writes AGENTS.md and does not support it as the only instruction file.

A symlink on any path the upgrade touches refuses the whole of its step 4. CLAUDE.md, .marvin/CLAUDE.marvin.md, .marvin, .marvin/agents, .marvin/backups, .docs, .claude/agents and their ancestors are all tested. The CLAUDE.md → AGENTS.md monorepo layout hits this, as does a .claude/agents symlinked into a dotfiles repo. It is a refusal for you to clear, not a bug: replace the link with a real file (for CLAUDE.md → AGENTS.md, a CLAUDE.md containing @AGENTS.md), or move it aside for the run. Writing (or, for the persona clean-up, deleting) through a link destroys files outside the repository while git status stays clean, with nothing backed up to reconcile from.

Renamed from agent-operating-kit. Existing users switch once with claude plugin uninstall agent-operating-kit@emprove followed by claude plugin install marvin@emprove. Installed projects are untouched by the rename.

The marketplace moved to its own repo. If you added it from the kit repo before, registered as zenosyne or emprove, remove it once with claude plugin marketplace remove zenosyne (or emprove) and add it from the address under Install. claude plugin marketplace list shows what you currently have.

What the plugin's hooks do

The plugin ships its hooks in hooks/hooks.json. They only act in a project the kit is installed in (.marvin/ present as a real directory, not a symlink); everywhere else they exit silently. Each mode key below lives in .marvin/PROJECT-INFO.md and is listed on Settings.

SessionStart

scripts/marvin-session-start.sh runs on startup, resume, clear and compact, so it fires again after every compaction. It adds two things to the session's context:

  • A version-drift check. It compares the plugin's own version with the project's installed kit_version (.marvin/PROJECT-INFO.md frontmatter, numerically, part by part). On a mismatch it prints one line. If the project is older, it prints the safe two-session update procedure, ending at /marvin:upgrade-agent-os. If the project is newer than the plugin, it says so and points at updating the plugin instead, since running the upgrade there would downgrade the install. An unreadable or symlinked PROJECT-INFO.md, or a kit_version that is not a plain X.Y.Z in the frontmatter, counts as unknown and gets its own one-line nudge to run the upgrade skill, never a raw file dump.
  • The user-update format rules, by full path (.marvin/agents/user-updates.md), stating that they take precedence over any active output style. They are printed only when the project's effective outputStyle is not Marvin's own (marvin:marvin, which carries the same block from hooks/user-update-rules.txt).

It never writes a file, never blocks the session, and always exits 0, including when .marvin, plugin.json or PROJECT-INFO.md is missing or unreadable. Editing hooks/hooks.json in the installed plugin cache does not survive the next plugin update. To turn it off for good, either disable the whole plugin (/plugin disable marvin) or turn off all hooks with the "disableAllHooks": true setting (see the hooks reference in the Claude Code docs). There is no flag that disables only this hook.

Rule enforcement

Since v0.38.0 the plugin also checks its rules mechanically. It never echoes message content and never blocks on a parse failure.

  • User-update gate (UserPromptSubmit and Stop, scripts/marvin-update-gate.sh): checks Marvin's messages for a <details> fold, a status emoji outside the legend, an incomplete issue callout, and a status update without its Next / Open questions tail. update_gate: advise (default; a note rides on the next prompt), block (a failing message is sent back once at Stop, and the next prompt carries the note as in advise) or off.
  • Sub-agent contract gate (SubagentStop, marvin:* only, scripts/marvin-subagent-gate.sh): a final message missing a reserved line (TRACKER:, GUARDRAILS:, or one its brief reserves) or over 25 lines goes back to the agent once.
  • Sub-agent rules (SubagentStart, scripts/marvin-subagent-rules.sh) and brief lint (PreToolUse on Agent, scripts/marvin-brief-lint.sh): a constant rules block for every persona, and advice when a brief lacks its run-report path, FINAL MESSAGE spec or DoD.
  • Context ladder (scripts/marvin-context-budget.sh): 70 / 80 / 90 % of the compaction window alongside the 400k / 700k budgets, the stricter one speaking (session-budget.md).
  • Output style: output-styles/marvin.md, selected per project by "outputStyle": "marvin:marvin". Install and upgrade offer it, and offer (never silently apply) a per-user disable of competing style plugins (scripts/marvin-style-plugins.sh, registry hooks/style-plugins.txt).

Worktree marker and sweep

When a marvin:* persona stops (SubagentStop), scripts/marvin-worktree-mark.sh --subagent-stop writes a marvin-owned marker file into that agent's isolation worktree's git admin dir. That marker is the only thing that makes a worktree Marvin's. The SessionStart sweep (scripts/marvin-worktree-sweep.sh --hook) and /marvin:clean-worktrees consider only marked linked worktrees physically under .claude/worktrees/, and keep one when any guard G1–G9 holds: locked, a session standing in it, a nested repo or worktree, recent activity, an operation in progress, uncommitted changes, commits in no branch other than its own, or a git-ignored .env* (outside wholly ignored folders such as node_modules/) or run-state file the project lacks. An unmarked worktree is never touched, only counted in a skipped: <n> worktree(s) not marked by Marvin — left to the app line. A hand mark refuses a worktree created over an hour ago. marvin-worktree-sweep.sh --at-risk (the upgrade's readiness report) lists every worktree under .claude/worktrees/, marked or not, whose G8 or G9 condition holds, as at-risk: lines, and removes nothing. worktree_sweep picks the mode: on (remove), check (report only; also the value when the key is absent or invalid) or off. The rules are in worktrees.md.

Run-state sync

scripts/marvin-runs-sync.sh (SessionStart, PostToolUse on Write|Edit|MultiEdit, SubagentStop, Stop) keeps Marvin's ledger, build briefs and agents' timestamped run reports in the project checkout's per-session folder .marvin/runs/<UTC start>-<session id>/<KEY|adhoc>/. That is the one copy readers use, even when the session works in a worktree that is later swept.

  • SubagentStop copies a marvin:* agent's named reports and never deletes the source. It overwrites a project copy only when that same agent carried it before (the gate's send-back), recorded in an ignored per-agent ledger .carried-<agent id>.
  • Stop catches up the ledger and build-brief writes made through Bash (>>), under the same rules, but only into a project key folder that already exists (a prune stays done) and never for timestamped reports (those are SubagentStop's).
  • <KEY> is a tracker key (AOS-12, T-1) or a GitHub issue's bare number (42). A run path whose key fails that rule gets a refused: key not allowed notice, never a silent skip.
  • It refuses any write through a symlink under .marvin/, git-ignores the folder, and gives carried copies the umask's normal mode. session-recovery.md covers a worktree that vanishes mid-task.
  • The upgrade skill's step 6b runs scripts/marvin-runs-migrate.sh to move a flat-layout .marvin/runs/ into this one.

Docker sweep and Docker lint

Docker sweep (v0.39.0). At startup, resume and clear, alongside the worktree sweep, scripts/marvin-docker-sweep.sh --hook removes Docker containers, networks, volumes and images labelled marvin.project=<this project>, marvin.checkout=<this checkout's path> and marvin.lifetime=throwaway whose owner worktree under .claude/worktrees/ is gone. It never touches a keep or main-owned one, a running container, or a resource without the project label, and never uses -f or a prune. It prints at most two lines (what it removed; main-owned throwaways still waiting) and stays silent when Docker is missing or its daemon is down. /marvin:clean-worktrees runs it too.

Docker lint (v0.39.0). PreToolUse on Bash (scripts/marvin-docker-lint.sh), for Marvin and sub-agents alike. It gives advice, never a block, when a command creates a Docker container, volume, network or image without both marvin.project and marvin.checkout (or --label-file); starts a compose stack (up/create/run) without -p/--project-name; or starts a throwaway MySQL/Percona container without --skip-log-bin (or --disable-log-bin, log-bin=OFF, log-bin=0) or a MariaDB one with --log-bin. It reads docker only in command position, never echoes the command and stays silent outside a Marvin project. docker_lint: advise (default) or off. The rules are in tidying.md.

Ticket lint

Since v0.39.0, PreToolUse on tracker writes runs scripts/marvin-ticket-lint.sh: the Atlassian, Linear and GitHub MCP issue tools, gh issue create|edit, and Writes of Local project-management/issues/*.md files. It runs for Marvin and sub-agents alike, and only on writes to the project's own tracker (pm_tool, project_key and tracker_coordinates); gh -R to another repo, another Jira project or a non-tracker MCP stays silent. Heredoc bodies and code in descriptions are skipped.

It enforces the pre-write half of ticket-filing.md's label check against the project's registry .marvin/agents/label-syntax.md: a create with no labels, a missing type:/area:/origin:, a type:bug without a severity, a non-epic create without size:, a size or severity stated only in the title or description, or a label value not in the registry. ticket_lint picks the mode: advise (the hook's default when the key is absent or empty: everything rides along as context), block (violations are denied with the reason, advisories ride along; an unknown explicit value also fails closed to block) or off. The installed PROJECT-INFO.md states block explicitly, so a project the install or upgrade skill touched enforces unless it chose otherwise. Its output names checks, dimensions and well-formed label values only, never the ticket's prose. The read-back half stays the writer's.

Codex, fleet mode and session clean-up

  • Codex validation (v0.40.0). OpenAI's Codex can take validation lanes beside or instead of Claude, diagnose a stuck task, or build on your request. Four keys set it (codex_handover, off by default, validation_strategy, codex_lanes, codex_evidence), and codex.md owns what they mean. Install asks them (upgrade too, once, when they are missing); /marvin:codex, /marvin:codex-astra and /marvin:codex-setup are your own entry points. When Codex is not ready, the work runs on Claude. See Codex lanes.
  • Fleet mode (v0.41.0). For parallel epics, /marvin:fleet turns the session into a master that runs one child orchestrator per epic. Fleet mode explains it.
  • Session clean-up (v0.42.0). The automatic worktree sweep removes only worktrees Marvin marked as its own (agent worktrees when they stop, a hand-made one via /marvin:clean-worktrees --mark); desktop session worktrees are left to the app. Run state lives in the project's .marvin/runs/<session>/<KEY>/, carried there by hooks from any worktree, with ledgers chained across sessions. An absent mode key never enforces. The upgrade's readiness step moves existing run state and defers sessions you say are still open.

Windows

The hooks and helper scripts are bash scripts, so on Windows they need Git for Windows (Git Bash) on the machine; they are written to run through it, from the Claude Code desktop app or the CLI.

  • Install Git for Windows with its default "Git from the command line and also from 3rd-party software" option.
  • Keep line endings as LF for this plugin's files (core.autocrlf=false); a CRLF-mangled bash script fails. A .gitattributes pins *.sh and hooks/*.json to LF, so a clone with core.autocrlf=true still gets working scripts.
  • Install the plugin as under Install.

The path-handling code (mh_path in scripts/lib/marvin-hook-lib.sh) is meant to treat C:\x\y, C:/x/y and /c/x/y as the same path, so the marker, sweep and run-state comparisons hold across the spellings Git Bash and the desktop app produce. A windows-latest CI job (Git Bash, core.autocrlf=false set before checkout) runs the worktree-sweep, session-hook, hook-library, ticket-lint, worktree-marker and run-state-sync suites. That job is added and its first run is pending, so Windows support is untested until it has gone green once (the job is non-blocking until then).

  • Each version targets a declared model set. Templates name tiers (orchestrator, heavy worker, small worker, micro, frontier). Two profile files alone map them to concrete models: templates/marvin/agents/model-profile.md for the Claude tiers and model-profile-codex.md for the Codex lanes.     The default profile runs the orchestrator on the heavy tier's model and offers the frontier tier as an opt-in at the max gate. The other profile puts the orchestrator a tier above the heavy worker over the same three workers, with no frontier tier: the main session then costs about 2× per token, and its orchestrator model needs 30-day data retention (not zero data retention). Install asks which one (an absent key reads as the default; any other value stops the upgrade's render and is a must-act finding for project-info). To switch, edit model_profile and run /marvin:upgrade-agent-os, which re-renders every model name from the new profile. Default efforts and the model-specific rules are the profile's: among them, the max gate recommends max over the frontier tier in the default profile and offers only max in the other, the micro tier always runs at high, and fully-specified code is micro-tier work (Escalation). Other models are unsupported: Marvin says so once when its session model differs from its profile's orchestrator.

  • Tracker-specific parts are confined to the coordinates line in ticket-filing.md plus templates/pm/<tracker>/ (currently linear/, jira/, github/ and local/; templates/pm/INSTALL.md holds the tool-neutral selection, sensecheck and project-key flow the skills follow). Adding a PM tool is one new folder (intake brief, tracker-config.md, stats-collection-brief.md) plus an entry in that reference's selection and sensecheck tables. Taxonomy and filing template carry over 1:1; sev1..sev4 labels stay canonical everywhere.

  • Tools with only three hierarchy levels use virtual milestones: a milestone:<slug> label on every epic in the milestone, encoded only in that label, so each converts losslessly into a native release or milestone once the tool or its connector allows. The conversion ships as a prepared brief, not just a rule.

  • The attribution policy is the owner's choice at install: keep Claude Code's default attribution (skip settings.json, delete the core rule), disable it entirely (settings.json with empty attribution.commit/attribution.pr, keep the "Attribution: none" rule), or brand it "Emprove Marvin (Claude)" (settings.json as shipped, with the branded core rule).
