v0.22.0 — git gets one owner, and a release gets a document

Gitflow replaces the milestone branch. Until now a milestone WAS a branch (milestone/<KEY>-<slug>), and everything else about git lived in whichever file happened to need it. Now main holds released state only, develop integrates, one feature/<KEY>-<slug> carries exactly one work item, and release/* and hotfix/* merge BOTH ways — skip the merge back and main carries commits develop has never seen, which the next release silently reverts. One guide, git-strategy.md, owns the whole model: the branch table, when a branch dies, who may tag (the orchestrator, never a sub-agent), how a version is spelled, how semver is classified by what a CONSUMER must do, and the eight ordered steps of a release cut. Every other file now names only the concrete branch or tag it needs and defers on the model. That rule is not tidiness: a second copy of the version-spelling rule had already produced a defect (release:vv1.2.0), which is why spelling and tag-message content are named in the owned set alongside the branch table.

A release now has somewhere to be written down. .docs/release-notes/ joins the documentation estate — one document per released version, its body identical to that version's annotated tag message. A tag message is not reachable by the documentation crawl and cannot be linked from an index, so without the document a release is findable only by whoever still remembers the version number. The note's mandatory scope: header carries the version's work-carrying issue keys, derived at the cut from the frozen commit range rather than recalled, because commits are what work actually leaves behind. This note's own scope: was derived over ec2cea4..HEAD — the commit where v0.21.0 shipped, since this repo had no tags before this one; the range is recorded because an over-broad one inflates the key set silently. It is the only answer to "what shipped in this version" that reads the same on every tracker — several have no per-issue version field at all. Milestones and releases are independent axes here: a milestone may span several releases, and a hotfix or a batch of reported bugs is a release belonging to no milestone.

A zero is no longer allowed to mean two things. The stats snapshot moves to schema 3. Before, tokens: null covered both "telemetry is not installed" and "the query matched nothing", and a scope that had quietly stopped resolving rendered as $0.00 — indistinguishable from work that was genuinely free. Now null means the telemetry DB is absent and nothing else; every other case is an object carrying state — ok, scope-unresolved or no-rows — beside the resolved key count and a control count of the project's own events. Renders print figures only for ok and name the state otherwise, and the stakeholder page omits its cost line entirely rather than implying the work was free. Collection gained a matching release:v<version> scope that resolves through the note's scope: header instead of the tracker. On Jira, whose connector cannot yet create a native release object, a release:v<version> label mirrors the tag on every issue that shipped until the existing conversion brief turns both label axes into fixVersions.

For consumers: upgrades/v0.22.0.md is the whole upgrade. Nothing moves or is renamed, so this release ships no migration script — the mechanical steps are all there is, and the branch-convention change in step 1 is the one that touches habits rather than files.

Tags start here. The twenty-one minor versions released before this one shipped untagged. Backfilling them would mean fabricating creation dates and inventing release prose that was never written, so tagging begins clean with the first release cut under the process this version describes. A retroactive backfill remains possible later, as its own tracked piece of work.

Upgrade

Nothing moves or is renamed, so there is no migrate-v0.22.0.sh — the steps below are the whole upgrade. As on every release, the kit-owned guides in .marvin/agents/ are re-rendered from the current templates and anything replaced is backed up to .marvin/backups/v0.22.0/; reconcile customisations from there.

  1. Your branch convention changes. milestone/<KEY>-<slug> is gone. Work runs on gitflow: main holds released state only, develop integrates, ONE feature/<KEY>-<slug> per work item, release/<version> and hotfix/<version> merged BOTH ways. A new guide, .marvin/agents/git-strategy.md, arrives with the refresh above and owns that model plus tagging authority (annotated tags, orchestrator only) and semver classification. Merge three things into CLAUDE.md, taking each verbatim from the current CLAUDE.core.md: the cascade row - Branching, versioning, tagging, or cutting a release — any git decision beyond a commit → \.marvin/agents/git-strategy.md``; the Git, branches, releases standing rule, REPLACING the old Milestone feature branching one; and the task-lifecycle paragraph's last sentence, which now ends …, and the closer merged and deleted its branch per \.marvin/agents/git-strategy.md`` — a task that closes without merging is work nobody will find. Finish and merge any in-flight milestone/* branch as it is; cut everything new from develop.
  2. Seed .docs/release-notes/index.md, and MERGE its row into the sub-folder table of the .docs/index.md you already have — every existing row and paragraph stays, that one row gets added. A seeded folder no row points at is unreachable from the crawl's entry point, which means it does not exist.
  3. Two prose edits the row-merge above does not cover — apply them by hand in your .docs/index.md, copying verbatim from templates/docs/index.md: append What one RELEASED version changed → \release-notes/`. to the "Where a new document goes" paragraph, and change the root-level-documents paragraph's folder count from "six" to "seven" (the seven folders above take everything…). Without these nothing routes a writer to release-notes/` and the count still lies.
  4. Release notes carry a mandatory scope: header. release-note is a new type: in document-standard.md, and for it scope: is required: that version's work-carrying issue keys (containers expanded), derived at the cut per git-strategy.md step 4 (previous tag, or the previous release's commit when you have no tags yet), never recalled, and the note records which range it used. Release-scoped reporting and cost resolve against that field and nothing else.
  5. Stats snapshot schema 2 → 3. tokens: null now means ONLY "the telemetry DB is absent". Otherwise tokens is an object whose state is ok / scope-unresolved / no-rows, always carrying scope_issue_keys and control_events, and carrying the figures only when state: ok. Renders print no currency figure at all for the other two states — not even zero. Snapshots already written to .docs/reports/ stay at schema 2: they are a record, leave them.
  6. Your .marvin/agents/stats-collection-brief.md accepts a third SCOPE, release:v<version>, which reads the note's scope: header instead of querying the tracker.
  7. Jira installs only: a release:v<version> label dimension joins milestone:<slug> (label registry v1.3.0) — on every issue that shipped, tasks included, while milestone: stays on epics; the same convert-milestones-brief.md converts both axes to fixVersions. GitHub, Linear and Local map releases natively and must NOT use the label. Re-running the intake brief seeds it.
  8. Restamp .marvin/PROJECT-INFO.md: kit_version: 0.22.0 and label_syntax_version: 1.3.0.
