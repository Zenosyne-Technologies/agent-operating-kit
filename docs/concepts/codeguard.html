Concepts

CodeGuard security rules

Project CodeGuard (CoSAI / OASIS, CC BY 4.0) is an optional companion plugin of third-party security rules. On a project that turns it on, the brief names the rules a task touches and both security validators check them. It adds checks on top of the kit's own security checklist and never replaces any of it.

The switch

One setting decides it: security_rules in .marvin/PROJECT-INFO.md, either kit or codeguard. Absent, empty or any other value reads as kit, and the kit checklist runs alone, as it always has. The kit pins the CodeGuard version it was validated against, v1.5.0, and installs it at project scope, so the plugin is recorded in the project's .claude/settings.json and teammates are offered it too (codeguard.md).

How it gets turned on

Install runs the offer as its own question, step 6e, on every install. Upgrade asks the same question once, only when security_rules is missing.

A failed install is reported with its output and never retried unpinned; the setting stays kit and the install carries on. An unanswered question runs no command. A re-install keeps a security_rules value that was already committed: one person's local plugin state never flips a project-wide setting, and only a yes that leaves the plugin ready changes it, to codeguard (install, upgrade).

On a codeguard project, each upgrade's check raises an issue callout when the plugin is disabled, removed or has drifted from the validated version, and never changes the setting. /marvin:project-info reads an absent key as kit and leaves it for upgrade to ask; /marvin:info shows the CodeGuard status beside the setting.

How a task uses it

Rules are named, never pasted: the brief lists rule IDs, and the builder and validators load only those, so context grows only by what the task touches. Select a persona to see its model and limits.

Which rules a task gets

At brief time Marvin uses the project's stack and the task's changed files to pick a row of the skill's language table. That row only narrows the candidates. From within it, the brief's security-surface item names just the topic rules whose tags match the task's security surface, never the whole row, plus three rules that always apply: codeguard-1-hardcoded-credentials, codeguard-1-crypto-algorithms and codeguard-1-digital-certificates. The tables stay in the skill; the kit cites them and never copies them, since they change upstream (briefing.md).

What the validators do

The Claude security validator loads the skill and checks the change against the named and always-apply rules. It may also scan the rest of the language row: an extra hit there goes in its run report as a note, unless it is itself an exploitable defect, which makes it an ordinary finding. A rule the brief should have named but did not goes in the run report only, since the builder cannot fix the brief (validation-agent.md).

Codex cannot load Claude skills, so Marvin reads the named and always-apply rule files and the forwarder renders them as a ### Rules block in the Codex security lane's prompt. The lane never gets the rest of the row, which would bloat its prompt. That rules text is transient: never committed, never filed (codex/security.md).

Both grade a violation by the kit's severity scale, by its impact if exploited, never by CodeGuard's own wording. One sentence carries that grading, word for word, in both validators, and the static gate's codeguard-grading check keeps the copies identical.

When the plugin is missing

A missing plugin never fails or blocks anything: not a task, not a validator, not a release. Marvin tells you once per session, with the command that installs it, and the task runs on the kit checklist alone. An install is recorded per checkout path, so a copied or moved checkout reads as unavailable until the plugin is installed there again with the same command.
