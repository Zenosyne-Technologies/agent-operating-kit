# v0.40.0 — Codex (ChatGPT) third-party validation

**Consumers act once:** run `claude plugin update marvin`, follow the update procedure the SessionStart notice prints (`upgrades/v0.40.0.md`), and answer the upgrade's Codex question — or leave it unanswered, which keeps Codex off.

**Why.** Marvin's validators are fresh Claude agents; a second vendor sees what one model family systematically misses. Marvin now hands work to OpenAI Codex through the `codex` Claude Code plugin. A project that never opts in sees no change and no Codex call.

**Settings.** Four `PROJECT-INFO` keys, owned by `.marvin/agents/codex.md`:
- `codex_handover: off | ask | auto` is the consent for every automatic handover. Under `ask`, only the question tool's own answer counts; no answer means no handover.
- `validation_strategy: claude | codex | four-eye | claude+lanes` picks which validation lanes run on Codex, and `codex_lanes` lists them for `claude+lanes`. In four-eye, Claude runs first and Codex tags each finding `new`, `recurring`, `regression` or `dup`; both must pass. A security FAIL is never overruled by the orchestrator.
- `codex_evidence: claude | codex` decides who runs the real checks. Codex's default sandbox has no network, browser or Docker, so a `codex` evidence run that needs them falls back to Claude evidence for that run.

**Auto debug.** Three tollgates on the Claude escalation ladder hand the situation to a read-only Codex diagnosis: a Stuck signal, the max gate, and an off-ladder validator failing twice. Each fires at most once per task.

**Codex builds** run only on the architect's command (`/marvin:codex build`), on their own ladder:
- rungs: the fast Codex tier at `high`, then the workhorse at `medium`, `high`, `xhigh`, then a user gate (hand back to the Claude ladder, `/marvin:codex-astra`, or stop);
- a Codex-built round is always validated by Claude;
- the `marvin:codex` forwarder works in its own worktree and commits for Codex.

The frontier Codex model is never routed by a rule; `/marvin:codex-astra` is the only path to it.

**Mechanics.**
- `scripts/marvin-codex.sh` is the only thing that touches the companion: `check`, `run` and `result` with guards (handover off, frontier without `--astra`, effort above `xhigh`, write access only for builds and review/security evidence runs) and a whole-run budget that returns `pending <id>` before the tool limit.
- A Codex run with no usable verdict counts as unavailable, never as a FAIL; the lane falls back to Claude, and work never stalls.
- Install step 6c and upgrade step 4a ask the settings; `/marvin:codex-setup` checks availability and walks the install, asking before each step. Marvin never logs in for you.

**Models.** On a ChatGPT login the Codex service rejected `gpt-6.1-sol` and `gpt-6-luna` (HTTP 400) in a live probe on 2026-10-16. The Codex profile therefore uses `gpt-5.6-sol` and `gpt-5.6-luna`, which completed; the frontier row keeps `gpt-6-astra`, unverified on that login.

**Acceptance.**
- Rule-5 scratch install from the branch (`claude -p --model haiku`, Local tracker, 2026-10-16): the answers `ask`, `claude+lanes`, `[review, security]` and `claude` landed in PROJECT-INFO after `ticket_lint`, the Codex rules and six lane briefs were installed, and the kit core stayed at 55 lines.
- Live replay in that repo:
  - with `codex_handover: off`, an orchestrator-path run was refused (exit 3);
  - `/marvin:codex review --base main` still ran, because the architect's command is the consent. Real Codex (`gpt-5.6-sol`, `high`, read-only) found both seeded defects, the result mapped to `CODEX: FAIL (review)`, and the forwarder's final message passed the SubagentStop gate.
- The install report omitted the 6c availability line, and the haiku install again left unrelated placeholders (AOS-221); both are follow-ups (AOS-241, AOS-221).
