# v0.22.0 — git gets one owner, and a release gets a document

**Gitflow replaces the milestone branch.** Until now a milestone WAS a branch (`milestone/<KEY>-<slug>`), and everything else about git lived in whichever file happened to need it. Now `main` holds released state only, `develop` integrates, one `feature/<KEY>-<slug>` carries exactly one work item, and `release/*` and `hotfix/*` merge BOTH ways — skip the merge back and `main` carries commits `develop` has never seen, which the next release silently reverts. One guide, `git-strategy.md`, owns the whole model: the branch table, when a branch dies, who may tag (the orchestrator, never a sub-agent), how a version is spelled, how semver is classified by what a CONSUMER must do, and the eight ordered steps of a release cut. Every other file now names only the concrete branch or tag it needs and defers on the model. That rule is not tidiness: a second copy of the version-spelling rule had already produced a defect (`release:vv1.2.0`), which is why spelling and tag-message content are named in the owned set alongside the branch table.

**A release now has somewhere to be written down.** `.docs/release-notes/` joins the documentation estate — one document per released version, its body identical to that version's annotated tag message. A tag message is not reachable by the documentation crawl and cannot be linked from an index, so without the document a release is findable only by whoever still remembers the version number. The note's mandatory `scope:` header carries the version's work-carrying issue keys, derived at the cut from the frozen commit range rather than recalled, because commits are what work actually leaves behind. It is the only answer to "what shipped in this version" that reads the same on every tracker — several have no per-issue version field at all. Milestones and releases are independent axes here: a milestone may span several releases, and a hotfix or a batch of reported bugs is a release belonging to no milestone.

**A zero is no longer allowed to mean two things.** The stats snapshot moves to schema 3. Before, `tokens: null` covered both "telemetry is not installed" and "the query matched nothing", and a scope that had quietly stopped resolving rendered as $0.00 — indistinguishable from work that was genuinely free. Now `null` means the telemetry DB is absent and nothing else; every other case is an object carrying `state` — `ok`, `scope-unresolved` or `no-rows` — beside the resolved key count and a control count of the project's own events. Renders print figures only for `ok` and name the state otherwise, and the stakeholder page omits its cost line entirely rather than implying the work was free. Collection gained a matching `release:v<version>` scope that resolves through the note's `scope:` header instead of the tracker. On Jira, whose connector cannot yet create a native release object, a `release:v<version>` label mirrors the tag on every issue that shipped until the existing conversion brief turns both label axes into fixVersions.

**For consumers**: `upgrades/v0.22.0.md` is the whole upgrade. Nothing moves or is renamed, so this release ships no migration script — the mechanical steps are all there is, and the branch-convention change in step 1 is the one that touches habits rather than files.

**Tags start here.** The twenty-one minor versions released before this one shipped untagged. Backfilling them would mean fabricating creation dates and inventing release prose that was never written, so tagging begins clean with the first release cut under the process this version describes. A retroactive backfill remains possible later, as its own tracked piece of work.
