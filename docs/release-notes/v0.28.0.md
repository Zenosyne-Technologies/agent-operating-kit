# v0.28.0 — visual validation (authoring spine) and a `finding:` reporting axis

Marvin validates completion and security but never *looked* at what it built. This release ships the authoring spine of a visual/design validation subsystem — the rules, personas, lifecycle slot and reporting contracts. It is **advisory** at the task level and never gates or bounces a task; it gates only at the UI release gate on sev1/sev2. The capture machinery that drives a live browser (the screenshot sweep) is deliberately a later increment; what lands here is everything that defines *how* a visual review works, all template-side and consumer-visible.

**A visual validator, wired into the lifecycle (AOS-123, AOS-124).** A new `marvin:validator-visual` persona (Opus-tier) and its rules guide `.marvin/agents/visual-validation.md` — fresh-eyes discipline (never the builder), surface acquisition, a graceful **degradation ladder** (no browser tool → SKIP; app not runnable → static/token analysis; surface unreachable → per-surface skip) so a missing UI never blocks a pass, a generic design/UX checklist (hierarchy, spacing, grid, grouping, consistency, contrast/a11y, responsive breakpoints, empty/loading/error states), a severity scale, and a machine-consumed FINAL MESSAGE. The task lifecycle in `CLAUDE.core.md` gains a conditional `[validate-visual]` step — UI tasks only, after the completion + security validators pass, before the documenter; `validation-agent.md` cites it as advisory at task, a sweep at milestone, and gating (sev1/sev2) at release.

**A screen catalog to resolve against (AOS-125).** Surfaces are named, not guessed: a docs-native, index-based screen catalog at `.docs/handbooks/developer/screens/index.md` (route · how to reach — auth + seed · breakpoints · deeper detail), and two new `PROJECT-INFO.md` keys — `screens_guide` (the top-level pointer into it) and `visual_validation` (`per-task|milestone|off`, default per-task).

**The builder declares what it touched (AOS-128).** The machine-parseable FINAL MESSAGE (`briefing.md`) gains a reserved `SURFACES:` line — the builder's own list of screen-catalog entries it created or changed (`NONE`/omitted for non-UI work), parallel to the existing `INFORMATION:`/`GUARDRAILS:` reserved lines. That declaration is authoritative; the orchestrator's diff heuristic (changed files → screen catalog) is a safety net that only *adds* under-declared surfaces, never overrides the builder.

**A dedicated `finding:` axis (AOS-130).** The label registry (`label-syntax.md`) bumps to **v1.4.0** with a new optional `finding:` dimension (value `visual`) — chosen over an `area:design` value because `area:` is required and single-valued and would collide with a finding's real component. `finding:` is orthogonal: a visual bug keeps its `area:`/`type:` and is *also* sliceable as design load. Applied to issues the visual validator raises.
