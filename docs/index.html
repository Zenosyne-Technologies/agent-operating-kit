The Agentic Operating System

Give your AI software team an operating system

Not another enormous prompt. Marvin is an orchestrator with a name, a personality and a memory. It plans, briefs specialised sub-agents, sequences their work and verifies it, but never bulk-implements.

What Marvin is

Marvin is a reusable agentic operating system for AI-assisted software projects, installed as a Claude Code plugin. Install it into a repo and that repo gets an orchestrator, plus the machinery that makes agent work auditable: size-routed model-tier dispatch, a cascading ruleset that keeps context proportional to the task, task lifecycles gated by a definition of done (DoD) with two adversarial validators in sequence, a versioned label registry feeding collect-once reporting, three living product handbooks, and, with the companion token-telemetry plugin, token and dollar cost down to the individual tracker issue.

It is for anyone running real software delivery through Claude Code and tired of "done" without evidence. It works with Linear, Jira, GitHub Issues or a Local markdown tracker, and installs a lean, self-contained payload in any repo. Marvin is built and operated under the same rules it installs.

A failed gate sends the task back to its build tier with the findings. The full lifecycle lets you select any persona for its model, job and limits.

Before build, sizing decides who works. When a build is stuck, escalation reads the failure pattern and climbs, rethinks or asks you. Around the loop covers everything else that keeps it honest, and fleet mode runs several epics at once.

What you get

An orchestrator with a name

Marvin stays in character for the project's lifetime, with a memory file it manages itself that survives context compaction.

Size-routed dispatch

Every task carries a size: label, and the label plus the brief's completeness decide which model tier builds it, down to a micro tier for mechanical work. The heavy tier's model is the sub-agent ceiling. After each failed round Marvin reads the failure pattern, and only at max does it ask you (Escalation).

A DoD-gated lifecycle

No task enters build without verifiable done-statements on the tracker issue. Fresh validators, never the builder, try to falsify them afterwards: completion first, then security. Anything web-facing is checked in a real browser (Playwright or direct browser driving), because an API-level curl check is not browser end-to-end testing.

A cascading ruleset

One always-loaded core (your CLAUDE.md plus the kit core it imports) holds only what applies to every turn. Per-activity rules live beside it and are cited in briefs, never pasted in.

A versioned label registry

Type, area, severity, origin and size on every item an agent creates or edits, with backfill-on-touch for legacy issues. This is what makes statistics possible at all.

Collect-once reporting

One stats snapshot per collection run, three renders on top of it: architect digest, milestone close-out, and a stakeholder page with no agent internals.

Three living handbooks

Developer, user and admin wikis in the project's docs, Obsidian-compatible, each page naming the code paths it documents so the docs agent amends instead of duplicating.

Security discipline

Secrets never committed or pasted into the tracker, dependency changes vetted and pinned, every brief naming its security surface, and security-critical design kept with Marvin.

Your PM tool, set up

A labelled, deduped intake structure created for you in Linear, Jira or GitHub Issues, or a self-contained markdown tracker inside the repo (PM tools).

Cost visibility, optional

With the token-telemetry companion: dollars per issue, per milestone and per tier, in the same snapshots and reports. Everything degrades silently without it.

Who is Marvin

Named for the Hitchhiker's android: the brain the size of a planet is canon, the depression is not. Smart, thorough, with a keen eye for detail and management; young and snappy. Marvin questions everything that does not add up: a brief that contradicts the code, a "done" without evidence, a number that appears from nowhere.

Its memory is its own to manage. Noteworthy findings (decisions, surprises, hard-won gotchas) go into MEMORY.md as they happen, before context compaction can lose them. Marvin reads it when a session starts and tidies it at milestone close so it never rots. Nothing goes in that the repo, the tracker or the handbooks already record.

That memory is also what lets Marvin keep sessions short. A plugin hook measures the session's context from its transcript (no telemetry needed), and Marvin plans, winds down and stops cleanly on the 400k / 700k budgets and the 70 / 80 / 90 % context steps. It writes the handoff and suggests /compact or a fresh session with a one-line resume prompt. Nothing is ever blocked. A project can move the budgets and the window with session_soft_ktokens, session_hard_ktokens and context_window_ktokens (session-budget.md).

The discipline stack

Each of these is one guide in the installed cascade. Reference lists them all, and Around the loop shows where each one acts.

  • Context proportionality. CLAUDE.md and the kit core it imports (.marvin/CLAUDE.marvin.md) are the only always-loaded files, and they hold only rules that apply to every turn. Everything else lives in the .marvin/agents/ cascade and is loaded only while that activity is happening. Briefs cite the file; they never paste its content.
  • Brief discipline. Every sub-agent brief carries the env preamble, exact scope, ownership boundaries, the exact branch plus autocommit instructions, idempotency, and a machine-read final message of 25 lines at most. The full report goes to a gitignored run report under .marvin/runs/ that Marvin opens only to act on a finding. No policy changes mid-run (briefing.md).
  • Guardrails, the DO NOT framework. One guide owns what an agent must not do. Every prohibition resolves to one of four dispositions: do the safe thing instead, stop and clarify, ask for approval from above, or skip and report. A blocked sub-agent follows a fixed chain (sub-agent → Marvin → you), commits whatever safe work it finished and names the block; no agent treats silence as approval (guardrails.md).
  • Labels as infrastructure. A self-contained, versioned registry: type, area, severity, origin and size on every item agents create or edit, plus backfill-on-touch for unlabelled legacy issues. An unlabelled item is invisible to reporting. The taxonomy, a filing template, dedupe rules and QA-sweep conventions are also published as a guide inside the tracker (label-syntax.md).
  • Collect once, render many. A per-tracker stats brief snapshots every label dimension into versioned JSON. The three renders read that snapshot as is, and a render without a fresh same-day snapshot starts by collecting one. The stakeholder page strips agent internals entirely: product progress only (reporting.md).
  • Traceability by convention. One guide owns everything git: a gitflow branch model, annotated tags only Marvin may cut, and semver classified by what a consumer must do. Agents autocommit finished work, atomic and selectively staged, and every commit message starts with its tracker key as <KEY>: <message>, so commits, branches and costs all resolve back to the PM tool (git-strategy.md).
  • The DoD as the contract. The planner writes it onto the issue before build starts. It is what the builder targets, what two independent validators attack, what the documentation agent documents against, and what the close comment quotes.
  • Security and secrets. Secrets are never committed and never pasted into PM-tool surfaces. A leaked secret is a sev1: rotate first, discuss second. Dependency changes are sized m or larger and get advisory checks with pinned versions (security.md).
  • Handbooks that stay alive. The developer handbook explains the software's logic and the why behind it; the user and admin handbooks give plain-language guides per module. Pages carry sources: frontmatter naming the code paths they document, so the documentation agent finds every affected page with one grep and amends it (handbooks.md).
  • Code that documents its own surface. Every new or changed public class or method carries a contract docblock (summary, parameters, return, errors) in its ecosystem's own idiom: PHPDoc, TSDoc, Javadoc, PEP 257, rustdoc, GoDoc. It states WHAT the contract is; a non-obvious inline comment explains WHY (documentation-agent.md).
  • Token economics. With telemetry installed, Marvin writes a context sidecar (issue key, project, size, a one-line summary) at each task start, and the telemetry hooks stamp it onto every captured event. Cost joins to issues, milestones and tiers for free, an effective-dated price table turns tokens into dollars at query time (every figure carries the date of the rate it used), and closed issues get a one-line cost figure. Without telemetry every cost output is omitted silently (token-economics.md).
